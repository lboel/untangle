Get a useful report before you add services.

Build the checkout, then measure its code. The first complexity report needs no account, index, embedding model or running service.

On Linux or macOS, use Node.js 22 (22.13+) or 24+ and pnpm 10.34.5. The npm package is not published yet; use the Untangle repository. Repository access is required until the public launch. For a new checkout:

Try Untangle on itself. 
git clone https://github.com/lboel/untangle.git
cd untangle
pnpm setup:local
UNTANGLE_CLI="$PWD/apps/cli/dist/index.js"
untangle() { node "$UNTANGLE_CLI" "$@"; }

setup:local installs the locked dependencies, builds the workspace and prints the first complexity report. It also prints absolute CLI commands and MCP configuration. The shell function makes the later examples work in this terminal.

Prefer the individual build commands? 
pnpm install --frozen-lockfile
pnpm run build
node apps/cli/dist/index.js complexity

Use pnpm setup:local --skip-build after a build you already trust, or pnpm setup:local --dry-run to inspect the plan without executing it.

Analyze your own repository

The shell function above works in the same terminal. Replace /path/to/your/project before running these commands: 

cd /path/to/your/project
untangle complexity
untangle init --offline --dry-run

The analysis reads your sources. The initialization command previews configuration; omit --dry-run only when you want to write it.

Next, connect a file to its feature or add indexed search and your agent host. No service setup is needed for code or declared feature analysis.

Connect the requirement to the feature it serves.

Start with an existing specification and a declared feature map, or a file from a search result. See the full feature scope, tests, owners and missing evidence in one local report.

With a specification and feature map

Select a file with --path. Untangle returns every matching declaration and measures the whole feature, including its helpers and shared implementation. 

untangle product --path=src/accounts/lookup.ts \
  --format=json

Without a specification

Choose a feature identifier and a real source file. Preview a minimal declaration, then review its boundaries and add the intent, tests and ownership you can establish. 

untangle product --draft --feature=accounts.lookup \
  --path=src/accounts/lookup.ts --format=json

When no manifest exists, --draft prints a review draft to stdout. It writes no feature map and invents no owners, requirements or test coverage. After review, save the returned draft object as untangle.features.json; the full report is not the manifest.

Run these examples from your project after the local setup above. Replace src/accounts/lookup.ts with a real repository-relative file and choose your own feature identifier. An existing untangle.features.json is read by default; use --manifest=PATH for another file.

Attach a real test run to the feature report

If your project uses Vitest, explicitly run its tests and capture the original results against the before/after source inventory. Replace the test path with your own: 

untangle product --path=src/accounts/lookup.ts \
  --run-tests -- pnpm exec vitest run src/accounts/lookup.test.ts

The command runs without a shell. Failures, skipped tests and sources changed during execution remain visible. Declared test files alone do not count as passed tests.

Initialize with an existing vision or specification

untangle init detects languages, workspaces, ignore rules and local context, then prepares a reviewable configuration. The document and map paths below must already exist in your project: 

untangle init --offline --dry-run \
  --vision=docs/vision.md --spec=docs/spec.md \
  --feature-map=untangle.features.json

Preview with --dry-run, then omit it to write the configuration. --offline skips service probes. Initialization does not invent a spec, assign owners or start recording searches.

Three layers of complexity.

From individual functions to the features they support and the effort it takes an agent to find them.

  • Repository complexity

    Analyze cognitive and cyclomatic complexity, inspect dependencies and call paths, and find the hotspots behind a coding task.

    AST metrics, file and symbol graphs. Results state their scope and coverage.

  • Complexity per feature

    Connect vision and specifications to declared features, code, tests and ownership. See how much complexity each feature carries, where code is shared and which evidence is missing.

    Feature reports, complexity budgets and actionable hints for agents.

  • Search-based monitoring

    Record real search journeys: queries, candidates, navigation and a confirmed target. Compare search effort alongside the complexity of the code found.

    Local lexical, symbol, semantic and hybrid search. Recording is opt-in.

Connect the analyzers you use.

Add Sentrux, SonarQube or another analyzer through an explicit extension manifest. Untangle provides the common harness: invoke configured providers, collect their evidence and report what ran, failed or was not measured.

Install and configure each provider first. Extensions can use a binary, container or HTTP endpoint; they are enabled explicitly by the operator. Provider manifests are installed separately. 

untangle extensions list --format=json
untangle scan --feature=accounts.lookup --format=json

Use your declared feature identifier. File-scoped findings can be related to its declared files; repository-wide values remain repository context.

Sentrux
Collect metrics from a configured binary provider.
SonarQube
Read existing project measures from a configured server. This does not trigger a new Sonar scan.
Your analyzer
Use SARIF, JUnit XML, generic findings or generic metrics through the extension runtime.

All providers support the same goal: reduce complexity. External measures retain their definitions alongside Untangle's own metrics. Provider failures and missing coverage stay visible; a collected report alone does not mean every analyzer passed.

What supports the feature

  • References to vision and specification
  • Selected code and test files
  • Supplied test results tied to the current source
  • Declared owners and missing or unverified links

Set complexity budgets per feature. As functionality grows, the report shows where its implementation exceeds those limits and needs attention.

The report checks the declared mapping and its evidence. It does not independently certify feature behavior or ownership.

Let real searches guide the next improvement.

Keep local journey records and revisit comparable tasks as the repository changes. Use recurring search difficulties to decide where code, documentation or feature boundaries need a closer look.

Repeated query reformulation
Investigate names that differ between the product, documentation and code.
Many plausible candidates
Investigate overlapping responsibilities or feature boundaries that are hard to distinguish.
Long navigation paths
Investigate scattered implementation, difficult dependencies or unclear ownership.
A direct route to the confirmed target
A useful signal of findable structure. Read it alongside complexity and feature evidence.

Start a session explicitly, link the agent's searches and confirm the target. These patterns are hypotheses to investigate, not automatic diagnoses. Index coverage, agent context and search strategy can also explain the effort. Recording begins when the host opts in, not when you run init.

Read search effort alongside code complexity.

A small function can be hard to find. A large function can be easy to find. The two measurements answer different questions.

Search effort and target-code complexity remain separate; they are never combined into one score. Embeddings help retrieve code. They do not measure its complexity.

What makes search journeys comparable?

Untangle records the ranking configuration, embedding profile, index generation and immutable corpus revision. The caller can declare its agent model, harness, strategy, task class, task mix and prior context; reports keep differing contexts in separate cohorts. This context is declared, not independently verified. Legacy journeys with incomplete context stay visible, but cannot establish a reliable comparison. Current reports summarize cohorts, including completed and abandoned tasks; built-in time-series and before/after trend views are not available yet.

What is available in this release?

Repository analysis, declared feature reports and explicitly recorded Search Journeys are available. Automatic feature detection, historical feature baselines and autonomous refactoring remain planned. Missing parser coverage and unresolved graph endpoints remain visible in reports.

The default path stays local.

In the standard setup, code is processed by local or self-operated services; remote endpoints are an explicit operator choice.

  1. Telemetry is off by default. A Search Journey starts explicitly. Searches count only when the host links them to that session; navigation counts only when the host or agent explicitly reports it.

  2. Journey free text is opt-in.
    Goals, queries and optional feature identifiers default to fingerprints generated with workspace-local, domain-separated HMAC-SHA-256. Failed-search and free abandonment details are omitted unless text retention was explicitly enabled. Source chunks are never journey data.

  3. Fingerprints are pseudonymous, not anonymous or encrypted. Metadata still remains: locators, ranks, scores, explicit tool names and an optional controlled abandonment reason code stay local even without text retention. The HMAC key is stored separately, and someone with the complete local state can test guesses. Journey files remain until the operator deliberately removes them.

Enable local indexed search

Search needs Qdrant; service embeddings also need Ollama and the configured model. --embedder=offline avoids Ollama. It uses deterministic vectors, without language-model semantics; lexical and symbol search remain available. init checks services; it does not start them or download models. 

untangle init
untangle doctor
untangle index
untangle query "your coding task" --require-fresh

Run from the target repository after providing the configured services. Inspect doctor before indexing. Queries read the index; rebuild it or use watch --index as sources change.

Agents can hand a search result's filePath to untangle_product as path. Start a Search Journey explicitly to record search effort; an MCP connection alone starts no monitoring.
